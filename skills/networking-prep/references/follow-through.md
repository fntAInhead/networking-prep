# After the event

## Capture actual interactions

Read the event and relevant saved notes. Ask only for missing details necessary to capture the user's experience:

- Whom they actually met and, if known, when.
- What they discussed and anything the user learned firsthand.
- What each person explicitly promised or requested.
- Desired next steps and any explicit timing.
- What felt natural or difficult, if they want coaching.

Accept brief, imperfect notes. Distinguish what the user remembers from what they are unsure about. Do not convert preparation objectives or rehearsal dialogue into meeting outcomes. If the event/contact choice is ambiguous, clarify before attaching notes to the wrong person.

Save actual notes as **user-reported interaction** evidence with capture date and meeting date if known. A newly reported fact does not become independently verified web research. Preserve disagreements with older sources and flag any practical implication for the next conversation.

## Interaction HTML companion

After creating or updating an event's `interactions.md`, also create or regenerate `interactions.html` in the same event folder. Match the user's supplied interaction-record visual reference: attendee header and status, meeting date, a concise confirmation banner, post-networking notes and next-meeting navigation, separate cards for what stood out and shared connection, and a commitments table with owner, basis, timing, and status. Give every attendee their own section and state; never combine separate attendees' conversations or commitments. Include only information already present in `interactions.md`; do not infer a meeting, relationship, promise, date, or status. Keep the Markdown file as the source of truth and unchanged for formatting. If the HTML offers copy or export actions, make them reflect the saved Markdown facts exactly. Label browser-only state accurately so it is not mistaken for a change to the Markdown record; an Add Commitment control must explain that the Markdown source needs updating to keep both records in sync.

Record commitments in a small table:

| Commitment | Owner | Basis | Timing | Status |
| --- | --- | --- | --- | --- |
| Explicit promise or requested action | User / attendee / unclear | User-reported note and date | Stated timing or unspecified | Open / completed / declined / uncertain |

Distinguish an actual commitment from a suggested next step. Do not invent deadlines or mark completion from a draft. Ask about an unclear owner only when needed to act or draft accurately.

## Draft follow-ups

Use actual notes, the user's tone, the relationship stage, and the stated goal. A useful short draft normally contains a genuine reference to the discussion, the promised item or an honest offer, and one clear next step.

### Event thank-you emails

When the user chooses follow-up drafting, identify possible recipients from actual interaction notes; a supplied attendee list may help with names, but attendance alone does not mean they met. Handle recipients one at a time: ask whether to draft for or skip the first person, then collect any missing details for that person before moving to the next. Never combine multiple attendees into one question. Do not treat a general request to draft follow-ups as consent to write to everyone, and do not draft for anyone the user skips. If the user has already explicitly selected or declined a person, preserve that choice without asking again. Ask only for details not already in their notes. For each selected person, useful prompts include:

- What stood out in your conversation?
- What real connection, shared interest, or point of common ground do you have with this person?
- Did either of you make a specific promise or request?
- What would you like the email to accomplish, if anything?

Accept brief notes and allow the user to skip any prompt. Do not invent a connection, meeting, promise, enthusiasm, or follow-up action. Keep each thank-you email under 150 words, including greeting and sign-off. Draft one per selected person, personalize each to that person's actual conversation, and save them as **draft, not sent**. If the user declines a recipient or says they are not interested, do not draft for that person.

When there are no actual meeting notes, ask for the key detail or draft an explicitly first-contact message if that fits the user's request. Never say `great meeting you` based only on an event attendee list or a simulation. Do not invent enthusiasm, agreement, introductions, or promises.

Check proposed attachments and links against what actually exists. Do not claim a document is attached or a resource was sent. If the user has promised a resource that is not yet available, mark the draft as needing that item and keep the commitment open.

Save drafts in the event's `follow-ups.md` with the intended person, channel if supplied, actual-note basis, unresolved items, and status **draft, not sent**. Provide short wording options only when useful, rather than generating several near-identical messages by default.

Sending, typing a message into a social platform, connection requests, and scheduling reminders are outside this drafting workflow. Proceed only if separately requested and under the applicable tool rules. Do not create an automation to track commitments automatically.

## Improve future preparation

Update relationship context with actual interactions and the user's explicit corrections. Preserve the source and date, and keep speculative observations tentative. Mark explicitly adopted preferences as profile updates; keep coaching suggestions separate until adopted.

For a later event, reuse confirmed contact identity and interaction history, refresh current roles and recent developments, and recommend ways to continue the relationship. A past promise remains open until the user reports its outcome. The user's actual experience takes precedence for their preferences; a prior hypothetical persona does not establish anything about the real person.
